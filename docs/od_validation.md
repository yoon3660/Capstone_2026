# 실측 TCS OD 대조 — 통행거리가 길다, 그런데 그게 결론을 지킨다

> 한 줄: **우리 통행거리가 실측보다 61~71% 길다.** 그래서 우리는 충전 수요를
> **과대추정**하고 있고, *"2026 설엔 안 막혔다"* 는 결론은 **보수적인 쪽으로 틀렸다.**

입력: `data/raw/tcs_od/tcs_od_2026{02,03}.csv` (팀원 수집, #61)
코드: `scripts/validate_trip_length.py` · `scripts/validate_tcs_od.py`

## 0. 먼저 — 팀원 결과가 원본에서 재현된다

팀원이 원본 CSV 와 가공된 `tcs_od_gyeongbu.parquet` 을 **둘 다** 줬다. 그래서 받은
parquet 을 그냥 쓰지 않고 **원본에서 다시 만들어 대조했다.**

```
python scripts/build_tcs_od.py          # 원본 CSV → tcs_od_all.parquet
python scripts/build_tcs_offices.py     # 영업소 42개 (중심선 최대 이격 1.465 km)
python scripts/build_tcs_od_gyeongbu.py # → tcs_od_gyeongbu.parquet
```

| | 결과 |
|---|---|
| 행 수 | 34,440 = 34,440 ✅ |
| `volume_veh` 합계 | 6,129,985 = 6,129,985 ✅ |
| 13개 열 전부 | **최대 차이 0** ✅ |

**비트 단위로 같다.** 파이프라인이 재현된다는 뜻이고, 이건 받은 파일을 믿는 것과
다른 종류의 확인이다.

## 1. 검증이 조용히 비어 있었다 (#97)

돌려 보니 숫자가 나오는데 **그 숫자가 검증이 아니었다.**

### `validate_tcs_od.py` — 0행을 검증하고 "저장 완료"

```
검증 가능 행: 0 / 1,640
coverage 요약:  count 0.0  mean NaN ...
저장 완료: data/processed/tcs_od_validation.parquet   ← 그리고 저장했다
```

`period` 라벨이 안 맞았다. 스크립트는 `"202602"→holiday` 로 바꾸려 했는데:

| | 실제 값 |
|---|---|
| `traffic_gyeongbu.parquet` | `seollal2026` · `base202603` |
| `tcs_od_gyeongbu.parquet` | `holiday` · `normal` |

**`"202602"` 는 어느 쪽에도 없다.** 날짜와 방향은 완벽히 맞았는데(2026-02-13~22 ·
2026-03-06~15 · DOWN/UP) **라벨 하나로 검증 전체가 비었다.**

> 더 나쁜 것은 **조용하다는 것**이다. 종료코드 0 으로 끝나고 파일까지 남긴다.
> 사람도 CI 도 못 잡는다. 그래서 **검증 가능 행이 0 이면 저장하지 않고 실패**하게 했다.

### `validate_trip_length.py` — 기간과 방향을 안 걸렀다

OD 전체를 합쳐 쓰고 있었다. 그래서 **설 연휴 시나리오를 설 + 평시를 섞은 것과** 비교했다.

**드러난 신호:** 상행과 하행 결과의 "실측" 열이 **완전히 같은 숫자**였다.

| | 합침 (전) | **holiday 만** (후) |
|---|---:|---:|
| 평균 통행거리 | 35.4 | **37.2~37.5 km** |
| `<190km` 비율 | 98.5% | **98.1%** |

**방향은 거의 무관하다** (DOWN 37.2 · UP 37.5). **기간은 영향이 있다** (설 37.3 · 평시 33.6).
그래도 둘 다 거른다 — *"거의 없다"* 는 지금 자료에서 그렇다는 것이고, 바뀌면 조용히 틀린다.

## 2. 고친 뒤 결과 — coverage

```
검증 가능 행: 1,425 / 1,640
coverage      평균 7.8%  ·  중위 4.6%  ·  최대 61.9%
coverage > 100%: 0행          ← 이게 통과 기준이다
```

**coverage 가 낮은 것은 정상이다.** 이 값은 *"OD 가 얼마나 완전한가"* 가 아니라
*"하류 콘존 교통량 중 **이 영업소에서 진입한** 몫"* 이다. 콘존은 상류 전체의 통행을
나르므로 한 영업소의 몫은 원래 작다.

| | 값 | 읽는 법 |
|---|---|---|
| **서울 하행** | **최대 61.9%** | 주 진입로답다. 가장 높아야 하고, 실제로 가장 높다 |
| coverage > 100% | **0행** | 넘으면 OD 가 교통량보다 많다는 뜻 — 모순이다. 없다 |

### 빠진 215행은 버그가 아니다

**VDS 공백이다.** 11개 영업소의 하류 콘존이 `traffic_gyeongbu.parquet` 에 아예 없다
(11 × 20일 + 일부).

```
통도사 · 기흥 · 기흥동탄 · 노포 · 독립기념관 · 칠곡물류 · 서울산 · 경산 · 왜관 ...
```

> **#59 때 "칠곡·평사가 비어 있다" 를 잘못 읽은 것과 같은 자리다.** 자료가 없는 것과
> 값이 0 인 것은 다르다. `traffic_daily_veh` 가 전부 NaN 인 것으로 구분된다.

## 3. 핵심 결과 — 통행거리

| | 우리 (하행) | 실측 | 차이 | 우리 (상행) | 차이 |
|---|---:|---:|---:|---:|---:|
| p25 | 21.5 | 13.6 | +7.9 | 20.1 | +6.5 |
| p50 | 41.2 | 24.9 | **+16.3** | 51.5 | **+26.6** |
| p75 | 82.6 | 43.0 | **+39.7** | 85.4 | **+41.7** |
| p90 | 135.8 | 73.2 | **+62.6** | 143.6 | **+70.4** |
| **평균** | **60.1** | **37.2** | **+22.8** | **64.0** | **+26.5** |
| **`<190km`** | 96.9% | 98.1% | **−1.2%p** | 96.0% | **−2.1%p** |
| 분위수 MAPE | **53.0%** | | | **69.0%** | |

**분포는 많이 다르다** (MAPE 53~69%. 교통량 검증은 12.1% 였다). 우리 통행이
**중간 구간에서 특히 길다** — 중위값이 1.7~2.1배다.

### 그런데 결론에 걸리는 값은 −1.2 ~ −2.1%p 다

우리 결론은 *"진입 SoC 66.5% 면 약 190 km 를 가는데, 통행 대부분이 그보다 짧아서
충전이 필요 없다"* 다. **거기에 걸리는 숫자는 `<190km` 비율 하나**고, 그건 거의 맞는다.

> 분포 모양이 틀렸는데 결론이 맞는 이유: **190 km 는 분포의 꼬리에 있다.** 중위값이
> 25 km 든 41 km 든 둘 다 190 보다 훨씬 작다. 분포가 **어디서** 틀렸는지가 중요하고,
> 틀린 곳이 결론이 걸린 곳이 아니다.

## 4. ⚠ 편향의 방향 — 이게 가장 중요하다

**우리 통행이 더 길다 → 190 km 를 넘는 차가 더 많다 → 충전이 필요한 차가 더 많다.**

```
          <190km      충전 필요
우리       96.9%        3.1%
실측       98.1%        1.9%      ← 실제는 우리의 약 0.6배
```

**우리는 충전 수요를 약 1.6배 과대추정하고 있다.** 그런데도 2026 설 재현에서
평균 대기 **0.003분 · 병목 0칸**이 나왔다.

> **즉 결론이 보수적인 쪽으로 틀렸다.** 실제 2026 설은 우리 재현보다 **더 한산했다.**
> *"안 막혔다"* 는 주장을 약화시키는 방향이 아니라 **강화하는 방향**이다.

### 발표에서 이렇게 쓴다

> *"통행거리 분포는 실측과 차이가 있습니다. 다만 저희 통행이 **실측보다 깁니다** —
> 즉 충전 수요를 **과대추정**합니다. 그런데도 쏠림이 안 보였으므로, 실제 2026 설은
> 저희 재현보다 더 한산했다는 뜻입니다."*

**먼저 말해야 한다.** Q&A 에서 지적당하면 같은 사실이 반대로 들린다.

## 5. 왜 통행거리가 긴가 — 답이 나왔다 (#99)

> **아래 가설이 맞았다.** `docs/od_destinations.md` 에 결과가 있다 —
> OD 의 조건부 목적지 분포로 바꾸니 **MAPE 53.0% → 8.1%** (하행),
> 평균 60.1 → 38.0 km (실측 37.2). **충전 필요 대수는 1,854 → 870대.**



지금 통행거리는 실측 OD 가 아니라 **콘존 교통량의 증감으로 추정**한 것이다 (#54).
교통량이 늘어나는 구간을 진입, 줄어드는 구간을 진출로 본다.

**짧은 통행이 과소대표되기 쉽다.** 한 콘존 안에서 들어오고 나가는 차는 교통량 증감에
흔적을 거의 남기지 않는다. 그래서 짧은 통행이 사라지고 평균이 길어진다 — 관측된
방향과 맞는다 (p25~p75 가 특히 부풀어 있다).

> ⚠ **이건 가설이다.** 확인하려면 OD 를 수요 생성에 **연결**해야 하고, 그건 #63 이다.
> 여기서는 **대조만** 했다 — OD 로 수요를 다시 만들지 않았다.

### #82 A 의 모순과 이어진다

#82 A 에서 충전 **시작** SoC 를 맞추면 **종료** 가 어긋났다. 실측 *"30% → 85%"* 는
같은 차가 30% 까지 떨어졌다가 85% 까지 채운다는 뜻인데, **그러려면 그만큼 달려야 한다.**

통행거리가 실측보다 **길다**는 것이 드러났으니, 모순의 뿌리가 *"통행이 너무 짧아서"*
는 **아니다.** 다른 곳이다 — 충전 규칙이나 목표 SoC 쪽을 다시 봐야 한다.
