# debug/lanes 디버그 로그

차로 프로파일(`lanes_gyeongbu.parquet`)이 나중에 이상하게 보일 때 **여기부터 본다.**

`docs/flow_params.md` §7~§11 이 "무엇을 왜 고쳤는가" 라면, 이 문서는 **지금 일부러
넘어간 것과 확인하지 못한 채 남은 가정**을 적는다. 고친 것은 테스트가 지키지만,
넘어간 것은 아무도 지키지 않기 때문에 글로 남긴다.

이 값들이 다르면 아래 숫자는 하나도 맞지 않는다. 비교 전에 먼저 확인할 것.

> 실제로 리뷰 중에 이 일이 있었다 (§3-①).

## 2. 확인된 것과 그 근거

넘어간 것을 읽기 전에, 무엇이 실제로 검증됐는지부터 구분해 둔다.

| 확인된 것 | 근거 |

## 3. 일부러 넘어간 것 / 확인하지 못한 가정

**우선순위 순.** "언제 문제가 되나" 가 지금 상황과 겹치면 그때 확인한다.

### ① 이정축이 사람마다 어긋나도 아무도 모른다  — 가장 위험

`data/processed/` 는 git 에 올라가지 않는다. 각자 `build_route.py` 를 돌려 만든
이정축 위에 교통량·충전소·차로 프로파일이 전부 얹힌다. **축이 다른 두 산출물을
섞어도 오류가 나지 않고, 교차검증은 "통과" 를 출력한다.**

- 언제 문제가 되나: 누가 `data/processed/` 를 통째로 주고받을 때, 오래된 작업
  디렉터리로 돌아갈 때, 중심선 CSV 가 갱신될 때.
- 증상: 병목 위치가 통째로 밀려 보인다. 값 자체는 그럴듯해서 눈치채기 어렵다.
- 확인: `build_route.py` 출력의 총연장이 415.058 km 인지. 교통량 정리본의 최대
  offset 과 같은지.
- 후속: `build_lane_profile.py` 가 둘을 대조해서 다르면 멈추게 한다. **미구현.**

### ② `LANES=1` 5개 링크의 정체를 모른다

상행 78.202~81.930 km 의 `3520811800` · `3520811803` · `3520811802` ·
`3520811801` · `3520811600`. `CONNECT='0'`(본선)인데 차로수가 1이다. 배포본 오류인지
다른 의미가 있는 값인지 **확인하지 못했다.** 지금은 이웃 중 적은 쪽(3차로)으로
메우고 `assumed` 로 표시만 해 뒀다.

- 언제 문제가 되나: 그 구간이 실제로 3차로가 아닐 때. 병목 위치가 바뀐다.
- 확인: `python scripts/inspect_links.py 3520811800 3520811803 3520811802 3520811801 3520811600`
  (좌표가 나오니 지도와 대조할 것). 다른 배포본과 비교해도 좋다.

### ③ 하행 `MAX_SPD=40` 링크 2개

`1870197300`(24.7 m) · `1961193201`(360.6 m). 고속국도 본선에 제한속도 40은
이상하다. 애초에 본선이 아닐 가능성이 있는데 `CONNECT='0'` 이라 필터에 걸리지
않았다.

- 지금 영향: **없다.** 둘 다 최소 셀 길이(0.5 km) 병합에서 흡수된다.
- 언제 문제가 되나: 최소 셀 길이를 줄이면 되살아난다.
- 후속 검토: `MAX_SPD` 를 본선 판정의 보조 신호로 쓸지.

### ④ 상행 241.252~256.992 km 가 편도 2차로 (15.7 km)

교차검증은 통과했다 — 그 구간 관측 피크가 2차로 용량(4,394 대/h) 이하라는 뜻이다.
하지만 **통과했다는 건 "모순이 없다" 는 것이지 "맞다" 는 게 아니다.**

- 언제 문제가 되나: CTM 을 돌리면 여기가 가장 강한 병목이 된다. 틀렸다면 없는
  정체를 만들고, 그 정체가 충전 수요 쏠림을 만든다.
- 확인: `python scripts/inspect_links.py --km 241 257 --direction UP`
- 참고: 중심선 원본에도 공식이정 241.1 km 부근에 불연속 보정이 있었다
  (`docs/T09a_centerline.md` §2). 기점이 달라 같은 지점은 아니지만, 이 부근을
  볼 일이 생기면 같이 확인할 것.

### ⑤ 되살린 연결로 40개의 타당성 (상행 16 / 하행 24)

본선이 덮지 못한 구간을 메우려고 램프를 되살린다. 실제로는 이정 약 102 km,
138~139 km, 246~247 km **세 곳에 몰려 있다.** 세 곳에서만 본선 링크가 끊긴다는
뜻인데, 왜 그 세 곳인지는 보지 않았다.

- 언제 문제가 되나: 되살린 링크가 최종 경로로 뽑히면 그 구간 차로수가 램프 값이
  된다. 1차로면 ②의 복구가 잡지만, 2차로면 **그대로 통과한다.**
- 확인: 실행 로그의 "되살린 연결로 링크" 목록. `inspect_links.py --km` 로 세 곳을 본다.

### ⑥ 교차검증의 사각지대

`check_lanes_against_observed` 는 **관측값이 있고 충분히 큰 곳**에서만 반증한다.

- 교통량 결측이 약 14% 다. 결측 구간은 검산되지 않는다.
- 차로수를 **많게** 잡은 오류는 원리상 잡히지 않는다. 그래서 복구는 적은 쪽으로
  하지만, 그 대가로 없는 병목을 만들 수 있다.
- 명절 피크가 없는 기간만 수집하면 필요 차로수가 과소 추정된다. 현재
  `seollal2026` + `base202603` 기준이다.

### ⑦ `build_lane_profile.py` 자체에는 단위 테스트가 없다

판단 규칙은 `src/evdt/io/lane_profile.py` 로 빼서 테스트했다(29건). 하지만 **규칙을
이어 붙이는 스크립트** — 이정축 변환, 복구 호출 순서, 저장 직전 검사 — 는
`tests/` 에서 `scripts/` 를 읽지 않는 리포 관례상 테스트가 없다. 지금은 실제 실행
결과로만 확인했다.

- 언제 문제가 되나: 스크립트 안에서 순서를 바꾸거나 단계를 끼워 넣을 때.
- 확인: 고친 뒤 반드시 끝까지 한 번 돌려보고, §1 표의 숫자와 대조할 것.

### ⑧ `lanes_gyeongbu.parquet` 을 읽는 코드가 아직 없다

하행 이정축을 바꿔도(§9) 아무 데도 영향이 없었던 이유다. 뒤집어 말하면 **이 파일의
프레임 가정이 코드로 고정돼 있지 않다.** 처음 읽는 쪽이 생길 때 방향별 offset 기준을
명시하고 테스트로 박을 것.

### ⑨ CI 가 실제로 돌지 않는다

main·브랜치·PR 전부 `startup_failure`, 실행시간 0초다. 워크플로 파일 자체는
문제없다(BOM 없음, LF, YAML 파싱 정상). 리포 단위 Actions 설정으로 보인다.

- 지금 영향: **위의 모든 테스트가 자동으로 돌지 않는다.** 회귀를 사람이 잡아야 한다.
- 확인: `gh run list --branch main`. 초록불이 하나도 없으면 여전히 안 도는 것이다.

### ⑩ 나머지

- `config/flow_params.yaml` 이 사람이 고치는 설정이자 스크립트가 덮어쓰는 생성물이다.
  손으로 쓴 주석이 다음 실행에서 사라진다. 파일을 둘로 나눌 것.
- k_jam 132 / 144 / 169 민감도 분석 미실시.
- 추석 holdout 수집 미실시.

## 4. 셀 분할과 앵커 간격

차로수 변경점은 CTM 셀 경계(앵커)가 된다. **현재 설정에서는 앵커를 하나도 버리지
않아도 된다.**

```
CFL 조건:  v_free * dt <= 셀 길이
  dt = 1.0분  ->  100 * 1/60   = 1.667 km 이상 필요
  dt = 0.2분  ->  100 * 0.2/60 = 0.333 km 이상 필요   <- 현재 설정
```

`dt_min` 은 #24 에서 1.0 이었고 debug/lanes 에서 **0.2 로 바꿨다.** 1.0 이면 0.5 km
셀에서 한 스텝에 셀 3개를 건너뛰기 때문이다 (`docs/flow_params.md` §3).

차로 프로파일은 저장 전에 이미 `min_cell_length_km`(0.5 km) 로 병합된다. 그래서
`lanes_gyeongbu.parquet` 의 모든 구간은 0.5 km 이상이고, 실제 생성 결과의 최소
앵커 간격은 다음과 같다.

| 방향 | 최소 간격 | 위치 |
|---|---|---|
| 상행 | 0.501 km | 192.108 ~ 192.609 km |
| 하행 | 0.518 km | 277.023 ~ 277.541 km |

0.501 km > 0.333 km 이므로 **모든 변경점을 셀 경계로 유지해도 CFL 을 만족한다.**
상행 4.020 ~ 4.553 km (0.533 km) 도 마찬가지다.

앵커를 병합해야 하는 상황이 생긴다면 규칙은 하나뿐이다: **차로수가 적은 쪽에
붙인다** (`merge_short_segments`). 용량을 크게 잡는 쪽으로 틀리면 있어야 할 병목이
사라지고, 그 오류는 §3-⑥ 때문에 아무것도 잡아내지 못한다.

> 1.667 km 로 계산했다면 `dt_min: 1.0` 을 보고 있는 것이다. debug/lanes 를 받지 않은
> 설정이다.
