## 1. UE 가 뭔가 — 한 문장

> **모든 운전자가 "내가 도착했을 때 얼마나 기다릴지" 를 알고, 각자 가장 빨리 끝나는
> 충전 계획을 고른 상태. 누구도 혼자 바꿔서 더 빨라질 수 없다.**

명절마다 같은 길을 다니며 "안성은 9시에 막힌다" 를 경험으로 아는 운전자다.
교과서의 Wardrop 균형이고, 나중에 SO(사후 최적해)와 비교할 기준선이다.

### S0 와 뭐가 다른가

| | UE | S0 |
|---|---|---|
| 보는 것 | 내가 **도착했을 때의** 대기 | **출발할 때 화면에 뜬** 대기 |
| 쏠림이 생기는 이유 | 각자 최선인데도 남는 혼잡 외부효과 | 같은 화면을 본 차들이 한꺼번에 몰림 |
| 구현 | 하루 단위 반복 균형 (`engine/ue.py`) | 매 Δt 정책 (`Policy.decide`, 다음 티켓) |

설계문서 §7.3 은 "UE 와 S0 가 사실상 같은 행동" 이라고 걱정했다. 이제 다르다.

## 2. 쏠림은 어디서 오나 — 균형인데도

UE 는 **각자에게** 최선이지 **모두에게** 최선이 아니다.
`test_equilibrium_leaves_captive_drivers_waiting` 이 가장 작은 예를 고정한다.

- 휴게소 A (200 kW, 충전 30분), B (150 kW, 충전 40분)
- 차 f: A·B 둘 다 갈 수 있다. 먼저 온다
- 차 c: 배터리가 적어 **A 밖에 못 간다** (captive). 1분 뒤에 온다

| | f | c | 합계 |
|---|---|---|---|
| **UE** — f 는 더 빠른 A 를 고른다 (자기에게 최선) | 30 | 29 대기 + 30 = 59 | **89분** |
| **SO** — f 를 B 로 보낸다 | 40 | 30 | **70분** |

f 는 10분 손해를 스스로 감수하지 않는다. 그 사이 c 가 29분을 기다린다. 이 19분이 이
프로젝트가 줄이겠다는 손실이다. 실제 코리도에서는 **배터리가 적어 앞쪽 휴게소밖에 못
가는 차**가 c 역할을 한다.

## 3. 어떻게 계산하나

### 선택지 = 충전 "계획"

설 하행에서는 장거리 차의 일부가 두 번 이상 서야 한다. 그래서 선택의 단위가 휴게소
하나가 아니라 **정차 휴게소들의 순서**다 (`engine/ue_demand.py`).

- 충전 규칙은 T-21 과 같다. `world/charge_decision.py` 의 함수를 그대로 쓴다
- 목적지에 SoC 여유(0.2)를 남기고 갈 수 있는 차는 UE 에 안 들어온다 (충전 수요가 아님)
- 휴게소까지는 안전버퍼 30 km 를 남기고 닿아야 한다
- 정차에서는 목적지까지 필요한 만큼 + 여유, 상한 0.8 까지 넣는다
- **정차 수가 가장 적은 계획만** 선택지로 둔다 (두 번이면 되는 사람은 세 번 서지 않는다)

### 비용 = 체류시간 (대기 + 충전)

후보가 전부 진행 경로 위에 있다. 어디서 서든 주행거리는 같다. 달라지는 것은 대기와
충전뿐이다. 늦게 설수록 도착 SoC 가 낮아서 충전이 길어지는데, 그 효과도 비용에 들어 있다.

### "나 혼자 바꾸면?" 은 근사가 아니라 정확하다

FIFO 에서 한 차의 대기는 **그 차보다 먼저 온 차들만** 정한다. 그래서 "나만 B 로 가면?"
은 B 의 실제 도착열에서 내 도착 시각 직전까지 쌓고, 나를 한 대 넣어보면 정확히 나온다
(`test_unilateral_cost_is_exact_for_single_stop` 이 실제로 한 대만 바꿔 굴린 결과와 비교).

이 계산은 **예약 원장**(`engine/ledger.py`, 설계문서 §5.4)이 한다. 큐 규칙을 부르는
곳은 시뮬레이터와 원장 둘뿐이고, UE 는 원장을 통해서만 큐를 본다. 원장은 S1 에서
"이미 배정된 차량의 미래 점유" 로 그대로 넓혀 쓴다.

### 반복 — 도착 순서대로 다시 고르기

| 반복 | 하는 일 |
|---|---|
| 0 | 빈 휴게소 기준 각자 가장 빠른 계획. **대기를 모르는 운전자**라 고출력 휴게소로 몰린다 |
| k | 진입 순서대로 한 대씩, 나머지 차들의 현재 계획을 보고 가장 빠른 계획으로 바꾼다 (1분 이상 줄어들 때만). 한 바퀴 뒤 전원을 다시 굴려 정확한 gap 을 잰다 |

도착 순서인 이유: 먼저 온 차들이 이번 바퀴에서 이미 골랐으므로, **한 번 서는 차는
한 바퀴 만에 정확한 균형**이 된다 (`test_single_stop_demand_is_exact_equilibrium_after_one_pass`).

**상대 gap** = Σ(내 체류 − 혼자 바꿨을 때 최선) ÷ Σ 내 체류.
"모두가 평균 몇 % 손해를 보고 있나" 로 읽는다. 0 이면 정확한 균형.

## 4. 완료조건 — 지킨 것과 문장 그대로는 못 지키는 것

| 완료조건 | 결과 |
|---|---|
| 반복 수렴, 최대 반복수·수렴 기준을 config 로 | ✅ `policy.ue.max_iter` (50), `gap_tol` (0.03), `min_gain_min` (1분), `max_stops` (3). 모르는 키는 로딩에서 거부 |
| 반복별 gap 을 solver_log Parquet 에 | ✅ `solver_log` 에 `iteration`, `rel_gap` 두 칸을 추가. UE 는 이 두 칸만 채운다 (MIP 칸은 비움) |
| 수렴 실패 시 run FAILED | ✅ `solve_and_log` 가 gap 이력을 남긴 뒤 예외 → run.status = FAILED |
| 휴게소 1곳이면 전원 그곳 | ✅ |
| 동일 조건 2곳이면 대기가 같아진다 | ⚠ **"같아진다" 는 못 지킨다.** 아래 ① |
| gap 이 반복에 따라 단조감소 | ⚠ **못 지킨다.** 아래 ② |
| 시드 고정 재현성 | ✅ 난수를 쓰지 않는다. 같은 수요면 입력 순서가 달라도 같은 결과. 시드는 수요 생성에만 있다 |

### ① 왜 대기가 "정확히 같아지지" 않나

차는 한 대씩 나뉜다. 두 휴게소에 81대가 오면 40 : 41 로 갈릴 수밖에 없고, 한 대 차이만큼
대기가 다르다. 반쪽 차를 보낼 수는 없다. 교과서의 "대기가 같아진다" 는 차를 물처럼
잘게 나눌 수 있다고 가정한 말이다.

대신 **균형의 정의 그 자체**를 검사한다. 누구도 혼자 옮겨서 줄일 수 없다 (gap = 0).
그리고 두 곳 평균 대기의 차이가 "한 대가 옮겨갈 때 생기는 차이"(충전 30분 ÷ 충전기
2기 = 15분) 이하인지도 본다. 80대(짝수)면 실제로 두 곳 평균이 102.0분으로 똑같다.

### ② 왜 gap 이 "단조감소" 하지 않나

한 번 서는 차만 있으면 gap 은 한 바퀴 만에 0 이 된다. 내려가기만 한다.

**두 번 이상 서는 차**가 문제다. 내가 첫 휴게소에서 충전하는 30분 동안, 뒤에 출발한
차가 나를 앞질러 다음 휴게소에 먼저 들어갈 수 있다. 그러면 내가 이번 바퀴에서 고른
계획이 다음 바퀴에는 최선이 아니게 된다.

균형에서는 대체 가능한 휴게소들의 비용이 같아진다. 그래서 1~2분 차이로 거의 동률인
차가 많고, 추월 한 번이 그 동률을 연쇄로 뒤집는다. 실측(설 수요 ×2, 고SoC):

```
반복 0  81.4%   대기를 모르는 선택
반복 1   3.1%
반복 2   2.4%
반복 3   3.0%   ← 올라간다
반복 4   3.1%
... 50회까지 2.2 ~ 3.2% 에서 오르내림
```

그래서 문장을 이렇게 바꿨다.
- 반복별 gap 을 **전부 기록**한다 (발표 그래프는 이 기록으로 그린다)
- 수렴 = gap ≤ 3%. 평균 체류 30분이면 1분이 안 되는 차이다
- 테스트: 첫 점이 가장 크고, 마지막 점이 기준 아래

시도했다가 버린 것 두 가지:
- **MSA** (개선 가능한 차 중 1/k 비율을 무작위로 옮기는 표준 방법): 휴게소 두 곳
  예제에서도 5% 근처에서 멈췄다. 한 대가 옮기면 그 휴게소 뒷차 전부가 밀리는 연쇄
- **감쇠** (두 번째 바퀴부터 바꾸고 싶은 차를 확률 1/k 로만 바꾸기): 4% 로 오히려
  나빠졌다. 한 번 서는 차의 정확한 최적반응까지 늦춘다

통째로 막히는" 모양으로 나온다.

## 6. 정해야 할 것

   SoC 로 쓸지, 출발 SoC 를 따로 둘지는 T-14 담당과 정할 일이다. 이 PR 은 config 를
   바꾸지 않았다.

   `demand.demand_multiplier` 로 훑으면 된다 (§5 나 의 표가 그 첫 줄).
