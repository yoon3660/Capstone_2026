# UE: 자율 선택 균형 (이슈 #29)

`src/evdt/engine/ue.py` · `engine/ue_demand.py` · `engine/ledger.py` · `io/demand_profile.py`
실행: `scripts/build_demand_profile.py` → `scripts/run_ue.py`
테스트: `tests/test_ue.py` (14), `tests/test_ue_demand.py` (17), `tests/test_ledger.py` (6)

```bash
python scripts/build_demand_profile.py      # 한 번만: 교통량 → 수요 프로파일 CSV 2개
python scripts/run_ue.py                    # config 그대로 (출발 SoC low, 수요 ×1, 시드 7)
python scripts/run_ue.py --soc high         # 출발 SoC 만 바꿔서
python scripts/run_ue.py --soc low --demand-multiplier 2
python scripts/sweep_ue.py                  # low·high × 수요 1·2·3 을 한 번에 돌리고 표로 비교
```

`--soc` / `--demand-multiplier` 는 config 파일을 고치지 않는다. 바꾼 값으로 새 실험을 만들고
scenario_id 뒤에 `__soc-high__dm2` 처럼 붙인다 (`ScenarioConfig.variant`). 그래서 칸끼리
run_id 가 겹치지 않고, 실제로 쓴 설정 전문이 `runs/<run_id>/config.yaml` 에 남는다.

## 1. UE 가 뭔가 — 한 문장

> **모든 운전자가 "내가 도착했을 때 얼마나 기다릴지" 를 알고, 각자 가장 빨리 끝나는
> 충전 계획을 고른 상태. 누구도 혼자 바꿔서 더 빨라질 수 없다.**

명절마다 같은 길을 다니며 "안성은 9시에 막힌다" 를 경험으로 아는 운전자다.
교과서의 Wardrop 균형이고, 나중에 SO(사후 최적해)와 비교할 기준선이다.

### S0 와 뭐가 다른가

| | UE | S0 |
|---|---|---|
| 보는 것 | 내가 **도착했을 때의** 대기 | **출발할 때 화면에 뜬** 대기 |
| 쏠림이 생기는 이유 | 각자 최선인데도 남는 혼잡 외부효과 | 같은 화면을 본 차들이 한꺼번에 몰림 |
| 구현 | 하루 단위 반복 균형 (`engine/ue.py`) | 매 Δt 정책 (`Policy.decide`, 다음 티켓) |

설계문서 §7.3 은 "UE 와 S0 가 사실상 같은 행동" 이라고 걱정했다. 이제 다르다.

## 2. 쏠림은 어디서 오나 — 균형인데도

UE 는 **각자에게** 최선이지 **모두에게** 최선이 아니다.
`test_equilibrium_leaves_captive_drivers_waiting` 이 가장 작은 예를 고정한다.

- 휴게소 A (200 kW, 충전 30분), B (150 kW, 충전 40분)
- 차 f: A·B 둘 다 갈 수 있다. 먼저 온다
- 차 c: 배터리가 적어 **A 밖에 못 간다** (captive). 1분 뒤에 온다

| | f | c | 합계 |
|---|---|---|---|
| **UE** — f 는 더 빠른 A 를 고른다 (자기에게 최선) | 30 | 29 대기 + 30 = 59 | **89분** |
| **SO** — f 를 B 로 보낸다 | 40 | 30 | **70분** |

f 는 10분 손해를 스스로 감수하지 않는다. 그 사이 c 가 29분을 기다린다. 이 19분이 이
프로젝트가 줄이겠다는 손실이다. 실제 코리도에서는 **배터리가 적어 앞쪽 휴게소밖에 못
가는 차**가 c 역할을 한다.

## 3. 어떻게 계산하나

### 선택지 = 충전 "계획"

설 하행에서는 장거리 차의 일부가 두 번 이상 서야 한다. 그래서 선택의 단위가 휴게소
하나가 아니라 **정차 휴게소들의 순서**다 (`engine/ue_demand.py`).

- 충전 규칙은 T-21 과 같다. `world/charge_decision.py` 의 함수를 그대로 쓴다
- 목적지에 SoC 여유(0.2)를 남기고 갈 수 있는 차는 UE 에 안 들어온다 (충전 수요가 아님)
- 휴게소까지는 안전버퍼 30 km 를 남기고 닿아야 한다
- 정차에서는 목적지까지 필요한 만큼 + 여유, 상한 0.8 까지 넣는다
- **정차 수가 가장 적은 계획만** 선택지로 둔다 (두 번이면 되는 사람은 세 번 서지 않는다)

### 비용 = 체류시간 (대기 + 충전)

후보가 전부 진행 경로 위에 있다. 어디서 서든 주행거리는 같다. 달라지는 것은 대기와
충전뿐이다. 늦게 설수록 도착 SoC 가 낮아서 충전이 길어지는데, 그 효과도 비용에 들어 있다.

### "나 혼자 바꾸면?" 은 근사가 아니라 정확하다

FIFO 에서 한 차의 대기는 **그 차보다 먼저 온 차들만** 정한다. 그래서 "나만 B 로 가면?"
은 B 의 실제 도착열에서 내 도착 시각 직전까지 쌓고, 나를 한 대 넣어보면 정확히 나온다
(`test_unilateral_cost_is_exact_for_single_stop` 이 실제로 한 대만 바꿔 굴린 결과와 비교).

이 계산은 **예약 원장**(`engine/ledger.py`, 설계문서 §5.4)이 한다. 큐 규칙을 부르는
곳은 시뮬레이터와 원장 둘뿐이고, UE 는 원장을 통해서만 큐를 본다. 원장은 S1 에서
"이미 배정된 차량의 미래 점유" 로 그대로 넓혀 쓴다.

### 반복 — 도착 순서대로 다시 고르기

| 반복 | 하는 일 |
|---|---|
| 0 | 빈 휴게소 기준 각자 가장 빠른 계획. **대기를 모르는 운전자**라 고출력 휴게소로 몰린다 |
| k | 진입 순서대로 한 대씩, 나머지 차들의 현재 계획을 보고 가장 빠른 계획으로 바꾼다 (1분 이상 줄어들 때만). 한 바퀴 뒤 전원을 다시 굴려 정확한 gap 을 잰다 |

도착 순서인 이유: 먼저 온 차들이 이번 바퀴에서 이미 골랐으므로, **한 번 서는 차는
한 바퀴 만에 정확한 균형**이 된다 (`test_single_stop_demand_is_exact_equilibrium_after_one_pass`).

**상대 gap** = Σ(내 체류 − 혼자 바꿨을 때 최선) ÷ Σ 내 체류.
"모두가 평균 몇 % 손해를 보고 있나" 로 읽는다. 0 이면 정확한 균형.

## 4. 완료조건 — 지킨 것과 문장 그대로는 못 지키는 것

| 완료조건 | 결과 |
|---|---|
| 반복 수렴, 최대 반복수·수렴 기준을 config 로 | ✅ `policy.ue.max_iter` (50), `gap_tol` (0.03), `min_gain_min` (1분), `max_stops` (3). 모르는 키는 로딩에서 거부 |
| 반복별 gap 을 solver_log Parquet 에 | ✅ `solver_log` 에 `iteration`, `rel_gap` 두 칸을 추가. UE 는 이 두 칸만 채운다 (MIP 칸은 비움) |
| 수렴 실패 시 run FAILED | ✅ `solve_and_log` 가 gap 이력을 남긴 뒤 예외 → run.status = FAILED |
| 휴게소 1곳이면 전원 그곳 | ✅ |
| 동일 조건 2곳이면 대기가 같아진다 | ⚠ **"같아진다" 는 못 지킨다.** 아래 ① |
| gap 이 반복에 따라 단조감소 | ⚠ **못 지킨다.** 아래 ② |
| 시드 고정 재현성 | ✅ 난수를 쓰지 않는다. 같은 수요면 입력 순서가 달라도 같은 결과. 시드는 수요 생성에만 있다 |

### ① 왜 대기가 "정확히 같아지지" 않나

차는 한 대씩 나뉜다. 두 휴게소에 81대가 오면 40 : 41 로 갈릴 수밖에 없고, 한 대 차이만큼
대기가 다르다. 반쪽 차를 보낼 수는 없다. 교과서의 "대기가 같아진다" 는 차를 물처럼
잘게 나눌 수 있다고 가정한 말이다.

대신 **균형의 정의 그 자체**를 검사한다. 누구도 혼자 옮겨서 줄일 수 없다 (gap = 0).
그리고 두 곳 평균 대기의 차이가 "한 대가 옮겨갈 때 생기는 차이"(충전 30분 ÷ 충전기
2기 = 15분) 이하인지도 본다. 80대(짝수)면 실제로 두 곳 평균이 102.0분으로 똑같다.

### ② 왜 gap 이 "단조감소" 하지 않나

한 번 서는 차만 있으면 gap 은 한 바퀴 만에 0 이 된다. 내려가기만 한다.

**두 번 이상 서는 차**가 문제다. 내가 첫 휴게소에서 충전하는 30분 동안, 뒤에 출발한
차가 나를 앞질러 다음 휴게소에 먼저 들어갈 수 있다. 그러면 내가 이번 바퀴에서 고른
계획이 다음 바퀴에는 최선이 아니게 된다.

균형에서는 대체 가능한 휴게소들의 비용이 같아진다. 그래서 1~2분 차이로 거의 동률인
차가 많고, 추월 한 번이 그 동률을 연쇄로 뒤집는다. 실측(설 수요 ×2, 고SoC):

```
반복 0  81.4%   대기를 모르는 선택
반복 1   3.1%
반복 2   2.4%
반복 3   3.0%   ← 올라간다
반복 4   3.1%
... 50회까지 2.2 ~ 3.2% 에서 오르내림
```

그래서 문장을 이렇게 바꿨다.
- 반복별 gap 을 **전부 기록**한다 (발표 그래프는 이 기록으로 그린다)
- 수렴 = gap ≤ 3%. 평균 체류 30분이면 1분이 안 되는 차이다
- 테스트: 첫 점이 가장 크고, 마지막 점이 기준 아래

시도했다가 버린 것 두 가지:
- **MSA** (개선 가능한 차 중 1/k 비율을 무작위로 옮기는 표준 방법): 휴게소 두 곳
  예제에서도 5% 근처에서 멈췄다. 한 대가 옮기면 그 휴게소 뒷차 전부가 밀리는 연쇄
- **감쇠** (두 번째 바퀴부터 바꾸고 싶은 차를 확률 1/k 로만 바꾸기): 4% 로 오히려
  나빠졌다. 한 번 서는 차의 정확한 최적반응까지 늦춘다

## 5. 실제 데이터로 돌린 결과 (경부 하행 · 설 2026 최대일 · −5 °C · 시드 7)

수요: 서울 진입 교통량 2/13 104,520 대 × EV 비중 8%. 목적지는 "각 지점을 지나가는
비율" 로 뽑는다 (50 km 62%, 100 km 46%, 200 km 22%, 이후 약 19% 가 끝까지).
휴게소 19곳 · 충전기 153기 (로컬 DB, 코리도 393 km).

북쪽 휴게소에 수요가 몰리고 남쪽은 텅 비었다. 병목 슬롯(휴게소×시간 평균 대기 ≥ 30분) 176개.

**그런데 이 크기는 SoC 가정에서 나온다.** `vehicles.soc_beta` = Beta(2,5) on [0.1, 0.95],
평균 34% 다. 설계문서 §2 표는 이것을 **"도착 SoC (직전 충전소 60 km 간격 가정)"** 라고
적었다 — Rupnik 이 쓴 것은 휴게소에 들어올 때의 SoC 다. 그런데 `synthetic_ev.py` 는
이 값을 **서울에서 출발할 때의 SoC** 로 쓴다. 평균 34% 로 집을 나서면 대부분이 첫
몇 휴게소밖에 못 간다 (captive). 그래서 "조정 실패" 가 아니라 "앞쪽 총량 부족" 이 된다.

### 나. 출발 SoC 를 "집에서 충전하고 출발" 로 바꾸면 (`--soc high`)

`vehicles.soc_profiles.high` = Beta(5,2) on [0.3, 0.95], 평균 76%. **근거 없는 대조군이다** —
"전날 집에서 채우고 출발" 을 흉내 낸 값이라, 실측 분포가 생기면 바꾼다.

| 수요 | 충전 필요 | 반복 → gap | 병목 슬롯 | 모습 |
|---|---:|---|---:|---|
| ×1 | 2,253 | 1회 → 0.15% | 0 | 수요 몫은 옥천 17% (충전기 몫 6%) 로 쏠리지만 **아무도 안 기다린다** |
| ×2 | 4,505 | 2회 → 2.38% | 0 | 평균 대기 0~4분, 최악 시간대 황간 22분. 막히기 시작하는 문턱 |
| ×3 | 6,598 | 3회 → 0.99% | 215 | 죽암~평사 **100~120분으로 비슷하게** 막힌다. 서울 쪽과 경주 이남은 0 |

(×2 를 gap_tol 1% 로 돌리면 50회 안에 못 가서 run 이 FAILED 로 남는다 — §4 ② 의 진동.)

×3 의 모습이 UE 의 특징이다. 서로 대체 가능한 휴게소들의 대기가 **같은 높이로**
올라간다 (균형이 대기를 고르게 편다). 쏠림이 "한 곳이 터지는" 모양이 아니라 "한 구간이
통째로 막히는" 모양으로 나온다.

- **low 는 수요 ×1 부터 이미 넘친다.** 몰림비가 수요와 상관없이 3.5 로 같다 — 몰리는 곳이

  병목이 0 → 218 로 뛴다. 균형이 수요를 여러 휴게소로 펴지만 구간 전체가 차면 다 같이 막힌다.
- 두 가정의 결과가 이렇게 다르므로, 발표에서는 **둘 다** 보여주고 어느 쪽이 현실에
  가까운지를 근거와 함께 말해야 한다.

## 6. 정해야 할 것

1. **출발 SoC 분포.** §5 가·나 가 결과를 완전히 가른다. 그래서 둘 다 config 에 이름을
   붙여 두고(`vehicles.departure_soc: low | high`) 따로 돌릴 수 있게 했다. 기본은 지금까지와
   같은 low. 어느 쪽을 "본 실험" 으로 할지는 T-14 담당과 정할 일이다.
2. **EV 비중·수요 배율.** 쏠림이 나타나는 수요 구간을 찾는 것이 RQ1 그 자체다.
   `demand.demand_multiplier` 로 훑으면 된다 (§5 나 의 표가 그 첫 줄).
3. **로컬 route 가 393 km 다** (팀 DB 는 415 km). 휴게소 위치가 조금 다르다.

## 7. 쏠림을 어떻게 확인하나 · 엔진이 나오면 무엇을 보나 · 어떻게 보여주나

### 쏠림 확인 — run 하나마다 `run_kpi` 에 남는 것

| 지표 | 뜻 | 쏠림이면 |
|---|---|---|
| `share_ratio_max` (몰림비) | 휴게소별 수요몫 ÷ 충전기몫 의 최댓값 | 1 을 크게 넘는다 (기흥 3.2) |
| `bottleneck_slots` | 휴게소×시간 평균 대기 ≥ 30분 인 칸 수 (설계문서 §8.1) | 0 이 아니다 |
| `wait_worst_station_min` | 휴게소 평균 대기의 최댓값 | 다른 휴게소와 크게 벌어진다 |
| `wait_p95_min` | 충전 정차 대기의 95% 값 | 평균보다 훨씬 크다 (꼬리가 길다) |
| `ue_final_gap` | 균형이 맞는지 | 3% 이하여야 위 숫자를 믿는다 |

**몰림비만 크고 병목이 0 이면 쏠림이 아니다** (고SoC ×1: 옥천 몰림비 2.9, 대기 0).
수요가 한쪽으로 가도 충전기가 버티면 아무도 기다리지 않는다. 둘이 같이 올라가야 쏠림이다.

한 번에 비교: `python scripts/sweep_ue.py` → SoC × 수요 배율 표.
시간대까지 보려면 DuckDB 한 줄 (`src/evdt/sql/station_hourly_wait.sql`).

### 엔진이 나오면 — UE 대비 무엇이 줄었나 (설계문서 §8)

같은 시드·같은 수요로 UE 와 엔진(S1~S4)을 돌리고 **같은 표**를 비교한다.

| 층 | 지표 | 읽는 법 |
|---|---|---|
| 헤드라인 | 코리도 총 사회적 비용 (원) = Σ 체류시간 × 시간가치 | UE 대비 몇 % 줄였나 (`dwell_total_h` 가 원재료) |
| 보조 | P95 대기, 병목 슬롯 수, 몰림비 | 꼬리와 몰림이 같이 줄어야 한다. 평균만 줄고 P95 가 그대로면 일부만 좋아진 것 |
| 공정성 | captive 차(한 곳밖에 못 가는 차)의 평균 대기 | UE 손실을 떠안는 쪽. 엔진이 이 차들을 살리는지 |
| 격차 분해 | UE → S4 → 완전예측 롤링 → SO | "남은 손실 중 몇 % 가 예측 오차, 몇 % 가 롤링 구조" 를 원화로 |
| 엔진 품질 | MIP gap, solve time P95, fallback 비율 (solver_log) | 엔진이 제시간에 제대로 풀었나. UE 의 rel_gap 과 다른 칸이다 |

엔진의 개선은 "UE 보다 몇 분 줄었다" 가 아니라 **"UE 가 남긴 손실(SO 와의 차이) 중 몇 %
를 회수했나"** 로 말하는 것이 강하다. §2 의 예라면 UE 89분, SO 70분 → 손실 19분 중
엔진이 몇 분을 되찾았나.

### 발표 시각화

| 그림 | 보여주는 것 | 재료 |
|---|---|---|
| **휴게소 × 시간대 대기 히트맵** (주연, T-20) | 어디가 언제 막히나. 위 = 서울, 가로 = 시각 | `station_hourly_wait` 한 줄 |
| UE vs 엔진 히트맵 나란히 | 같은 칸이 옅어졌나 — "개선" 을 한 장으로 | 두 run_id |
| 수요몫 vs 충전기몫 막대 | 쏠림을 숫자 하나 없이 설명 | charge_event + charger |
| gap 수렴 그래프 | UE 가 진짜 균형이라는 근거 | `solver_log` (`ue_gap.png`) |
| SoC × 수요 배율 표/히트맵 | 쏠림이 어느 수요에서 시작되나 (RQ1) | `sweep_ue.py` 결과 |
| 대기 시간 흐름 (한 휴게소) | 표시 대기(S0)와 실제 대기의 어긋남, 큐 진동 | `snapshot` `wait_min` + charge_event |
| 지도 위 휴게소 원 (크기=대기) | 코리도 전체를 한눈에 (Sprint 4, Plotly/deck.gl) | snapshot 의 위경도 |

히트맵은 **한 가지 색의 진하기**(옅음 = 0, 짙음 = 오래)로 그리고, 여러 run 을 나란히 놓을
때는 **같은 구간(0 / 10 / 30 / 60분 / 2시간 / 4시간)** 을 쓴다. 칸마다 색 범위가 다르면
"개선" 이 색 착시가 된다.
