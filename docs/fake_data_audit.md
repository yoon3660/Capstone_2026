# 가짜 휴게소 데이터 영향 검토 (2026-09-21)

## 무엇을 검토했나

`scripts/smoke_run.py` 는 배관 확인용으로 가짜 휴게소 3곳과 충전기를 만들었다. 문제는
이걸 **진짜 하행 코리도 `gyeongbu_down` 에 그대로** 넣었다는 점이다.

| 가짜 휴게소 | 가짜 거리 | 가짜 좌표 | 충전기 | 진짜 같은 이름 휴게소 |
|---|---|---|---|---|
| 안성휴게소(가짜) | 62.000 km | 37.0075, 127.2700 | 200 kW × 4 | 안성휴게소 **53.524 km** (A00005) |
| 천안휴게소(가짜) | 92.000 km | 36.8200, 127.1400 | 200 kW × 2 | 천안호두휴게소 **91.363 km** (A00034) |
| 옥천휴게소(가짜) | 185.000 km | 36.3100, 127.5700 | 200 kW × 6 | 옥천휴게소 **156.316 km** (A00103) |

거리와 좌표는 지어낸 값이다. 천안만 진짜와 637 m 차이로 우연히 가깝다.
(거리는 리뷰어 로컬 이정축 392.978 km 기준. 415.058 km 에서는 약 6% 늘어난다.)

`station`·`charger` 테이블을 읽거나 쓰는 코드를 **전부** 따라가서, 이 가짜 행이 결과나
설계에 영향을 줬는지 하나씩 확인했다.

## 1. 도로중심선 -500 m 보정 — 가짜 데이터와 무관하다

"천안 휴게소를 기점으로 -500 m 씩 보정했다" 는 기억이 있어서 가장 먼저 확인했다.

**결론: 무관하다.** 근거는 세 가지다.

**① 보정 코드는 휴게소를 읽지 않는다.** `scripts/load_centerline.py` 는 도로공사
중심선 CSV 하나만 읽는다. 보정 조건은 CSV 의 이정 간격이다.

```python
# 원본 이정 간격이 전부 0.1 km 인데 딱 한 곳만 0.6 km 다
if abnormal != [(241.1, 241.7, 0.6)]:
    raise ValueError(...)
gyeongbu.loc[gyeongbu["official_offset_km"] >= 241.7, "offset_km"] -= 0.5
```

git 이력 전체에서 0.5 km 를 빼는 코드는 이것 하나뿐이고, 처음 커밋(`0105ec1`)부터
이 형태였다. 휴게소나 천안을 참조한 버전은 없다.

**② 보정 지점은 천안이 아니라 금강휴게소 옆이다.** 공식이정 241.7 km 는 구서IC 기점
작업이정 241.2 km, 좌표로는 (36.279, 127.684) 부근이다.

| 지점 | 좌표 | 가까운 곳 |
|---|---|---|
| -500 m 보정 지점 | 36.279, 127.684 | 금강IC 1.0 km, 금강휴게소 |
| 가짜 천안휴게소 | 36.754, 127.226 | 독립기념관IC 0.8 km, 천안JCT |

둘은 약 80 km 떨어져 있다. 금강 구간은 선형개량으로 도로가 짧아진 곳이라, 옛 이정
표지가 남아 번호가 0.5 km 건너뛰는 것이 자연스럽다. 두 좌표가 실제로 약 100 m 떨어져
있다는 T-09a 의 확인과도 맞는다.

**③ 보정이 틀렸더라도 내부 정합성은 깨지지 않는다.** 휴게소, 콘존, 차로 프로파일,
셀 모두 **좌표를 같은 노선에 투영해서** 위치를 정한다. 이정 번호를 직접 쓰는 곳은
없다. 그래서 보정이 틀렸다면 영향은 총연장이 0.5 km 달라지는 것뿐이고, 데이터끼리
서로 어긋나지는 않는다.

### 대신 발견한 것: 상행 2차로 구간이 이 지점에서 시작한다

차로 프로파일에서 상행 **241.252 ~ 256.992 km 가 편도 2차로(15.7 km)** 다
(`docs/debug_lanes_log.md` §3-④). 그 시작점이 보정 지점(241.2 km)에서 **52 m** 떨어져 있다.

리뷰어는 이전에 디버그 로그에 "기점이 달라 같은 지점은 아니다" 라고 적었는데, **틀렸다.**
중심선 공식이정과 상행 offset 은 둘 다 구서(부산)가 기점이라 같은 축이다. 로그를 고쳤다.

이것이 뜻하는 바는 두 가지 중 하나다.

- 금강 구간 선형개량의 경계라서 **이정도 끊기고 차로 구성도 바뀌는** 실제 지점이다.
  그렇다면 2차로가 맞을 수 있다.
- 또는 이 경계 근처에서 표준노드링크 링크를 노선에 투영할 때 문제가 있다.

가짜 데이터와는 관계없다. 확인은 SHP 를 가진 사람이 할 수 있다.

```bash
python scripts/inspect_links.py --km 240 258 --direction UP
```

## 2. 결과가 실제로 틀어진 곳: T-17 셀 분할

`seed_cells.py` 가 `station` 테이블을 코리도 구분 없이 전부 읽어서 가짜 3곳이 셀 앵커가
됐다. 가짜 천안(92.000)과 진짜 천안호두(91.363)가 637 m 붙어 있어서, 셀 길이를 조금만
올려도 "보호 앵커끼리 너무 가깝다" 로 멈췄다.

오류 메시지에는 거리 숫자만 나오고 휴게소 이름은 나오지 않는다. **원인이 코드가 아니라
DB 안의 데이터에 있어서 코드를 아무리 봐도 보이지 않았다.**

debug/cells 에서 고쳤다 (`docs/T17_cells.md` §4). 가짜 데이터가 사라져도 설계는 바뀌지
않는다 — 1.667 km 를 불가능하게 만든 진짜 원인은 서울만남의광장(하행 기점 0.559 km)이고,
그 때문에 "휴게소 사이 짧은 셀 한 칸 허용" 규칙은 여전히 필요하다.

## 3. 수치는 맞지만 코드가 위험했던 곳

**T-05/T-06 적재(`load_chargers.py`)와 감사(`audit_charger_counts.py`).**
둘 다 경부선 코리도의 휴게소를 source 구분 없이 센다. `docs/T06_charger_audit.md` 의
282기는 가짜 데이터가 생기기 전에 계산돼서 맞다 (지금 다시 돌려도 282 = 282). 하지만
가짜 행이 있는 DB 에서 다시 돌렸다면 **38곳 / 294기**로 부풀었고, 감사는 가짜 3곳을
"DB n기, 공개데이터 0기" 불일치로 보고했을 것이다.

적재는 upsert 라서 가짜 행을 지우지도 않는다. 두 스크립트 모두 이제 가짜가 섞여 있으면
멈춘다.

**휴게소 이름 매칭은 안전했다.** 가짜 이름의 "(가짜)" 가 정규화 뒤에도 남아서
(`station_match_key("안성휴게소(가짜)") == ("안성휴게소(가짜)", None)`), 진짜 휴게소의
공개데이터 충전기가 가짜 쪽으로 잘못 붙을 수는 없었다. 직접 돌려서 확인했다.

## 4. 가짜 데이터 때문에 복잡해진 설계

**smoke 전용 코리도(`smoke_down`).** debug/cells 첫 수정에서 가짜 휴게소를 진짜와 분리하려고
만들었다. 진짜 휴게소를 쓰기로 하면서 필요 없어져 **없앴다.** 가짜 데이터를 격리하는
것보다 안 만드는 것이 더 단순하다.

**smoke_run 의 수요 대수(N_EV).** 가짜 휴게소 12기에 맞춰 150 으로 조정해 뒀었다. 진짜
세 곳은 28기라 300 으로 다시 잡았다.

**`require_no_smoke` 가드.** 예전 DB 에 남은 가짜 행 때문에만 존재한다. 팀원 모두의 DB 가
정리되면 지워도 된다. 지금은 비용이 거의 없고(COUNT 한 번), 없으면 같은 사고가 조용히
재발할 수 있어서 남겨둔다.

## 5. 가짜와 별개로 발견한 버그: validate_master 가 셀 저장 뒤 실패한다

`validate_master` 는 "모든 휴게소가 셀 하나에 매핑돼 있다" 를 검사한다. 그런데 셀 분할이
`station.cell_id` 를 채우지 않아서, **셀을 처음 DB 에 저장한 순간부터 35곳 전부가 "매핑
안 됨" 으로 실패**한다. `seed_vehicles.py` 가 이 검사를 부르므로 차종 적재가 깨진다.

`seed_cells.py` 가 휴게소마다 셀을 매핑하도록 고쳤다. 규칙은 **휴게소 지점에서 시작하는
셀(하류 셀)** — 충전을 마친 차가 본선으로 합류하는 곳이다. 저장 뒤 같은 트랜잭션 안에서
`validate_master` 를 돌리고, 실패하면 롤백한다. 테스트
(`test_writing_cells_without_station_mapping_breaks_validate_master`)가 이 회귀를 재현하고
고쳐진 것을 확인한다.

- **run 테이블의 seed=9999 기록.** smoke_run 실행 기록이다. `smoke_clean.py` 가 지운다.
  run 전체를 집계하는 분석 코드는 아직 없다.
