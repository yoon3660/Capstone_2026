## 3. 그래서 2/17·2/18 을 쓸 수 있나

**조건부로 그렇다. 다만 "검증일이라서 나쁜 날" 이 아니라 "설이라서 나쁜 날" 이다.**

### 쓸 수 있다고 보는 이유

- **검증일 중 나쁜 쪽이 아니다.** 2/17 38.3% · 2/18 45.1% 인데 2/21 은 64.7%,
  2/22 는 71.3% 다. 가장 걱정했던 두 날이 오히려 낫다
- **중위 APE 가 평균보다 훨씬 낮다** (22% 안팎). 큰 오차가 **소수 칸에 몰려 있다**는
  뜻이고, 그 대부분이 새벽이다
- 상행은 25~28% 로 더 낫다

### 그래도 못 하는 것

| | |
|---|---|
| **새벽 (0~5시)** | 하행 **90~96%**. **쓰면 안 된다** |
| **총량** | 모델/실측 **1.10~1.12** — 10% 과대. 수준이 아니라 **모양**으로만 써야 한다 |
| **2/21·2/22** | 64.7% · 71.3%, 총량 +28~36%. **빼는 것이 맞다** |

### 진짜 진단 — 달력 분류가 연휴 주간에 안 맞는다

**평시는 검증일이 보정일보다 거의 안 나빠진다** (12.7 → 14.0%). 일반화가 된다는 뜻이다.
**설은 7.6 → 48.0%** 로 6배가 된다.

처음에는 *"연휴를 하루(2/16)만 보고 나머지를 맞히라고 해서"* 라고 생각했다.
**그 설명으로는 안 된다.** 날짜 유형을 맞춰 보면:

| 검증일 | 요일 | 유형 | 보정에 그 유형이 | MAPE |
|---|---|---|---|---:|
| 2/17 | 화 | holiday | 있음 (2/16) | 38.3% |
| 2/18 | 수 | holiday | 있음 (2/16) | 45.1% |
| 2/19 | 목 | weekday | 있음 (2/13) | 36.4% |
| 2/20 | 금 | weekday | 있음 (2/13) | 32.4% |
| **2/21** | **토** | **weekend** | **있음 (2/14·2/15, 둘)** | **64.7%** |
| **2/22** | **일** | **weekend** | **있음** | **71.3%** |

**여섯 날 전부 그 유형이 보정에 있었다.** 미학습 유형 대체(fallback)가 아니다.
그리고 **보정 예시가 가장 많은 weekend 가 가장 나쁘다** — 학습량으로 설명되지 않는다.

> **2/14·2/15 는 설 *전* 주말이고 2/21·2/22 는 설 *후* 주말이다.** 달력 이름은 같고
> 교통 양상은 정반대다 — 하나는 귀성 전, 하나는 귀경 후다.
>
> 즉 **`weekday / weekend / holiday` 라는 축이 연휴 주간을 못 가른다.** 실제 구조는
> **귀성 → 연휴 → 귀경**이고, 그건 요일을 가로지른다.

총량 배율이 그대로 보여준다 — 2/17~2/20 은 1.10~1.12 인데 **2/21·2/22 는 1.28·1.36** 이다.
**규모 외삽이 귀경 구간에서 깨진다.**

**그래서 보정일 수를 늘리는 것보다 연휴 단계를 축으로 세우는 쪽이 먼저다.** 다만 그러면
단계별 보정일이 1~2일로 줄어 또 다른 문제가 생긴다 — 자료의 한계이지 코드의 결함이 아니다.

## 4. 고친 것 ① 생성기 — `period` 가 보정일에서만 비었다

### 증상

```
2/13~2/16 (보정)  period = NaN
2/17~2/22 (검증)  period = 'holiday'
```

`period` 로 거르면 **실제로 적합한 날은 전부 버리고 예측한 날만 남는다** —
측정 1,472,089대 중 **579,789대(39%)가 말없이 사라진다.**

### 원인

보정일과 검증일이 **다른 경로**를 탄다.

| | 경로 | 결과 |
|---|---|---|
| 보정일 | `fit()` → `solve_daily` | 8개 열만 남기고 **TCS 신원 열을 버린다** |
| 검증일 | `measured_od(tcs)` | TCS 프레임 **전체 복사** |

`estimate_od_daily.py` 의 `columns` 목록이 `period`·영업소 코드·이름·마일포스트를
떨어뜨리고 있었다.

### 수정

`TCS_IDENTITY` 를 두고 **양쪽 경로가 똑같이 들고 가게** 했다. 추정 행은 그 값이 없는
것이 맞지만 **열 자체는 있어야 한다** — 열이 없으면 concat 뒤에 "보정일 전체가 빈 것"
과 구분되지 않는다.

테스트: `test_fit_carries_tcs_identity_so_train_and_validation_match`
(수정을 되돌리면 **실패하는 것을 확인**했다).

## 5. 고친 것 ② 우리 쪽 — 조용히 축소되고 있었다

`od_profile.load_od_profile` 에 #62 결과를 그냥 넣으면 **성공한다.** 그런데:

```
평균 통행거리  40.50 → 39.52 km      ← 에러 없이 달라진다
```

`period` 로 거르면서 **외부 통행 5.57M대와 `departure_hour` 를 통째로 버린** 결과다.

### 수정 — 알고 쓰라고 요구한다

```
[중단] 이 OD 는 ['departure_hour', 'source'] 를 들고 있는데 이 함수는 그걸 쓰지 않는다.
  날짜·시간을 합치고 period 로 걸러 **일부만** 쓰게 된다.
  그래도 되면 accept_subset=True 로 명시하라 — 무엇이 빠지는지 찍어 준다.
```

`accept_subset=True` 로 쓰면:

```
[od_profile] holiday·DOWN 로 892,300 / 7,043,668대 (13%) 를 쓴다 · 안 쓰는 열 [...]
```

**13% 라는 사실이 화면에 찍힌다.** `period` 가 빈 행이 있을 때도 같은 이유로 거부한다.

> 기존 `tcs_od_gyeongbu.parquet` 은 그 열들이 없으므로 **아무것도 안 바뀐다.**

## 6. 남은 것 — 이 자료를 실제로 쓰려면

**아직 `demand.od_profile` 에 꽂을 수 없다.** 꽂으면 13% 만 쓴다.

제대로 쓰려면 `od_profile` 이 이 스키마를 **이해해야** 한다:

| 써야 할 것 | 지금 |
|---|---|
| **`departure_hour`** | 버린다 → #99 가 VDS 로 때운 자리를 되돌릴 수 있는 바로 그 열 |
| **외부 통행** (5.57M대) | 버린다 → 우리 OD 가 통째로 빼고 있던 통행 |
| `source` 별 신뢰도 | 안 본다 → 측정 21% / 추정·예측 79% |

> ⚠ 다만 **#100 이 먼저다.** 진입 위치를 VDS 와 TCS 중 어느 쪽으로 할지 정해야 하는데,
> 외부 통행이 들어오면 그 질문의 답이 바뀐다.
