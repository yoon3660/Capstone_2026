# 목적지를 실측 OD 에서 뽑는다 (#99)

> 한 줄: **통행거리 MAPE 53.0% → 8.1%** (하행). 교통량 검증(12.1%)보다 좋다.
> 그리고 **충전 필요 대수가 1,854 → 870대**로 절반 아래로 떨어진다.

코드: `src/evdt/io/od_profile.py` · 스위치: `demand.od_profile`

---

## 1. 무엇이 틀렸었나 — "목적지가 진입 지점과 무관"

지금까지 목적지는 `io/entry_exit.py::sample_exit_offsets` 가 뽑았다. 하류 경계를 훑으며
`exit_share` 확률로 빠지는 **위험률(hazard) 모델**이고, docstring 이 가정을 직접 적어 뒀다.

> *"진입 지점이 어디든 같은 규칙이 적용된다"*

서울에서 탄 차와 대전에서 탄 차가 **같은 이탈 확률 곡선**을 쓴다는 뜻이다.

### 실측 OD 로 재 봤다 (설·하행)

| 진입 | 실측 평균 | 옛 모델 | p50 실측 → 모델 |
|---|---:|---:|---|
| **서울** (물량 33%) | 36.4 | **61.8 km** | 16.8 → **63.1 (3.8배)** |
| 천안 | 53.1 | **40.8 km** | 34.9 → 20.7 (**너무 짧다**) |
| 대전 | 54.5 | **74.5 km** | 23.3 → 38.8 |

**단순한 편향이 아니다 — 틀린 방향이 기점마다 다르다.** 전역 곡선 하나로 모든 기점을
동시에 맞출 수 없다는 뜻이고, 그게 **기점·목적지 결합이 빠졌다**는 정확한 징후다.

서울이 전체 물량의 33%(489,013 / 약 1.47M)라 총합 편향을 서울 오차가 끌고 간다.
**#97 에서 본 *"통행이 실측보다 61~71% 길다"* 의 뿌리가 여기다.**

## 2. ⚠ OD 에는 시간이 없다

```
tcs_od_gyeongbu.parquet: period · date · start/end_office · direction · volume_veh · offsets
                         ^^^^ hour 가 없다 (일자별 집계)
```

**그래서 OD 는 "어디로 가나" 만 준다. "언제 타나" 는 그대로 VDS 가 준다.**

> 이걸 흐리면 **하루가 평평해진다.** 명절 피크가 사라지면 쏠림 자체가 없어지고,
> 이 프로젝트가 재려는 것이 없어진다. **시간축은 건드리지 않았다.**

### 잃은 것도 적어 둔다

위험률 모델의 `exit_share` 는 **시간대별**이어서 목적지가 시간에 따라 달라졌다.
OD 는 일자별이라 그게 없어진다. **기점 결합을 얻고 시간 변화를 잃는 교환**이고,
기점 쪽 오차가 3.8배였으므로 그쪽이 크다고 판단했다.

**일자별이라는 것은 자료의 한계이지 설계 선택이 아니다.** 시간대별 OD 가 생기면
그때 다시 본다.

## 3. 좌표 관례 — 진입 0 km 와 서울TG

모델의 코리도 진입점은 **offset 0.0 km**(양재)인데 가장 가까운 OD 기점은
**서울TG 12.941 km** 다.

**이건 오차가 아니라 같은 진입을 다르게 부르는 것이다** — TCS 는 요금소 거래만 보므로
"코리도 시작" 이라는 개념이 없다. 그래서 OD 를 켜면 **진입 위치를 OD 기점으로 맞춘다.**
맞춰야 통행거리가 실측과 **같은 자(尺)** 로 재진다.

### 조용히 맞추지 않는다

| | 최악 맞춤 | 그 지점 물량 | 물량가중 평균 |
|---|---:|---:|---:|
| **하행** | 12.941 km (코리도 진입) | **104,520대** | 4.41 |
| **상행** | 17.027 km | **560대 (0.1%)** | 2.58 |

`MAX_SNAP_KM = 18.0` 이고, 넘으면 **그 자리에서 터진다.** 멀리 붙은 차는 **다른 기점의
목적지 분포**를 쓰게 되고, 그 결과는 통행거리 평균 한 줄로만 보여서 알아채기 어렵다.

> 처음 구현에서 **맞춤 거리를 0.000 으로 보고했다.** `describe_snap` 에 이미 맞춘 값을
> 넘겨서 다시 맞춘 탓이다. *"조용히 맞추지 않겠다"* 던 보고가 **거짓 안심**이 되어
> 있었다. 맞추기 전 값을 따로 들고 있게 고쳤다 (테스트로 고정).

## 4. 결과

### 하행 — 거의 맞는다

| | 옛 수요 | **OD 수요** | 실측 |
|---|---:|---:|---:|
| p25 | 21.5 | **12.8** | 13.6 |
| p50 | 41.2 | **24.5** | 24.9 |
| p75 | 82.6 | **44.1** | 43.0 |
| 평균 | 60.1 | **38.0** | 37.2 |
| `<190km` | 96.9% | **97.6%** | 98.1% |
| **분위수 MAPE** | **53.0%** | **8.1%** | — |

### 상행 — 좋아졌지만 덜 맞는다

| | 옛 수요 | **OD 수요** | 실측 |
|---|---:|---:|---:|
| 평균 | 64.0 | **45.7** | 37.5 |
| **MAPE** | **79.1%** | **23.8%** | — |

**상행이 왜 덜 맞는지는 설명된다.** 맞춘 뒤의 통행거리는 **정의상 실측 OD 의 값**이다
(기점·종점 모두 OD 에서 온다). 그러면 남는 차이는 **기점 구성비** 한 곳에서만 올 수 있다.

| | 기점 구성비 차이 (총변동거리) | MAPE |
|---|---:|---:|
| 하행 | 0.392 | 8.1% |
| **상행** | **0.430** | **23.8%** |

**순서가 맞는다.** 원인은 **VDS 와 TCS 가 "어디서 타는지" 에 대해 다르게 말하는 것**이다.
#99 는 진입을 VDS 에서, 목적지만 OD 에서 가져오므로 그 불일치가 남는다.

> ➡ **#100 의 몫이다.** 그리고 거기서 따져야 할 것: **TCS 는 요금소 거래라 진입 위치의
> 더 직접적인 측정**이고, VDS 는 콘존 교통량 증감에서 **추정**한 것이다. 어느 쪽을
> 믿을지는 #100 에서 근거를 보고 정한다 — 여기서 조용히 바꾸지 않았다.

### 충전 필요 대수가 절반 아래로 떨어진다

```
하행 진입 EV 18,534대
  옛 수요   충전 필요 1,854대
  OD 수요   충전 필요   870대     ← 0.47배
```

**기준선이 움직이는 변화다.** 지금까지의 모든 결론(쏠림이 언제 생기나 · S0 · S1)이
다른 수요 위에 서게 된다. 한 시드 UE 로는 총 체류 143시간 · 병목 0칸 · 이탈 0대가 나왔다.

> ⚠ **정량화는 #101 이다.** 상·하행 × 시드 20 으로 재고, 수요 사다리
> (1,842 → 10,936)를 OD 수요로 다시 내서 **꺾이는 지점이 움직이는지** 본다.
> #97 에서 예상한 방향대로 **더 한산해졌다** — 그래도 그대로 보고한다.

## 5. 두 번 걸린 함정

### `scenario_id` 를 안 바꾸면 run 이 충돌한다

`od_profile` 을 기본 시나리오 파일에 직접 써 넣고 돌렸더니 거부당했다.

```
RunExistsError: 이미 등록된 실행이다: seollal_2026_down_base__S0__p100__s0001
```

**맞는 동작이다.** `od_profile` 은 **세계를 바꾸는 값**이라 `scenario_id` 가 같으면
옛 수요 run 과 OD 수요 run 이 **같은 run_id** 를 갖는다. 그러면 #101 의 비교가
**같은 run 을 자기 자신과 비교**한다.

```bash
# 이렇게 쓴다 — scenario_id 뒤에 __od 가 붙는다
cfg.variant("od", {"demand.od_profile": "data/processed/tcs_od_gyeongbu.parquet"})
```

기본 시나리오 파일은 `od_profile: null` 로 둔다. **키는 넣어 둬야 한다** — `variant()` 는
이미 있는 키만 덮어쓴다.

### 이름 문자열로 기간을 짐작하면 틀린다

`od_subset_for` 를 처음에 `scenario_id` 문자열로 썼다. 그런데:

```
scenario_id = "seollal_2026_down_base"
                                 ^^^^ "base" 가 들어 있다
```

이름에 `base` 가 있으면 평시로 분류하도록 썼으니, **설 연휴 시나리오가 평시 OD 를 쓸
뻔했다.** #97 에서 고친 것과 **똑같은 실패**다.

> 선언된 값만 본다 — `demand.period` 와 `corridor_id`. `variant()` 가 `scenario_id` 에
> 태그를 붙여도 이 둘은 안 바뀐다. 그리고 `PERIOD_ALIAS` 는 `validate_tcs_od.py` 와
> **같은 표**다 — 두 곳이 갈라지면 검증과 모델이 다른 OD 를 본다.

## 6. 쓰는 법

```bash
# 끈 상태 (기본) — 옛 결과가 비트 단위로 재현된다
python scripts/validate_trip_length.py --config config/scenario_seollal_down.yaml

# OD 를 켜고 비교
python scripts/validate_trip_length.py --config <variant 로 od_profile 을 켠 config>
```

테스트 13개 (`tests/test_od_profile.py` 12 + `test_config.py` 1).
지키는 것은 **"기점을 모르면 조용히 넘어가지 않는다"** 하나다.

| | |
|---|---|
| 비율대로 뽑히는가 | 3:1 OD → 3:1 |
| **기점마다 분포가 다른가** | ← #99 의 전부 |
| 진입이 기점으로 맞춰지는가 | 0 km → 12.941 |
| **너무 먼 진입은 터지는가** | 조용히 붙으면 남의 분포를 쓴다 |
| 맞춤 보고가 맞추기 **전** 거리인가 | 0.000 거짓 안심 방지 |
| 기간·방향이 걸러지는가 | 섞으면 반대 방향 목적지가 나온다 |
| **이름 문자열을 안 보는가** | `_base` 함정 |
| OD 만 켜면 거부되는가 | 기점이 하나면 뜻이 없다 |
