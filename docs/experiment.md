## 1. 왜 시드를 반복하나

시드 하나 = EV 집합 하나 (진입 시각 · 차종 · 출발 SoC · 목적지). 실제로 config 그대로 돌린
시드 20개의 평균 대기는 393분에서 445분까지 흩어졌다. 시드 하나만 보고 "413분" 이라고 말하면
그 안에 우연이 섞여 있다.
20개를 돌려 평균과 **95% 신뢰구간**을 내면 "진짜 평균이 이 범위에 있다" 고 말할 수 있다.
"A 가 B 보다 낫다" 는 두 구간이 겹치지 않을 때 말한다.

**신뢰구간** = 평균 ± t(0.975, n−1) × 표준편차 ÷ √n. run 하나의 KPI 가 표본 하나다.
시드 20개면 t = 2.09.

## 2. 완료조건

| 완료조건 | 어떻게 |
|---|---|
| `run_experiment.py` 가 시나리오 + 시드 목록을 받는다 | `--config`, `--seeds 1-20` (또는 `1,2,5`), `--soc`, `--demand-multiplier`, `--stage` |
| 시드마다 run 등록, run_id 는 `make_run_id()` | `…__UE__p100__s0001` … `s0020`. 테스트가 run_id 문자열까지 확인 |
| 시드 20개 이상, KPI 별 평균·95% CI | 20개 미만이면 거부 (`--min-seeds` 로만 낮춤). t 분포 구간 |
| 히트맵: 가로 시간, 세로 기점거리, 색 = 대기(또는 큐 길이) | `heatmap_wait.png`, `heatmap_queue.png` |

| 테스트: run 테이블에 시드 수만큼 행 | 두 번 돌려도 3행 (run_id 가 같아서 덮어쓴다) |

## 3. 히트맵 세로축이 offset_km 인 이유

#29 의 히트맵은 휴게소를 **같은 간격 줄**로 늘어놓았다. 그러면

- 옥천만남(153.8 km) 과 옥천(156.3 km) 은 2.5 km 떨어졌는데 한 줄씩 차지하고
- 건천(319 km) 과 경주(336 km) 사이 17 km, 칠곡(245) 과 평사(291) 사이 46 km 도 똑같이 한 줄이다.

가까이 붙은 휴게소들이 연달아 막히면 "긴 구간이 통째로 막힌" 것처럼 보이고, 먼 곳은 가까워
보인다. 도로 위에서 어디가 얼마나 넓게 막혔는지를 말하려면 세로축이 실제 거리여야 한다.

그래서 휴게소를 **제 기점거리에 두께 6 km 의 띠**로 그리고(이웃이 더 가까우면 중간에서 자른다),
사이의 도로는 비워 둔다. 기점거리는 DB 의 `station.offset_km` 그대로다 — 노선 좌표계를
415 km 로 바로잡기 전 값(393 km)이 남아 있으면 그 값으로 그려지므로, 팀 DB 로 돌릴 것.

## 4. 러너가 패키지로 옮겨간 이유

CI 에는 실측 데이터가 없다. "시드 3개 축소판이 끝까지 돈다" 를 테스트하려면 러너가 DB 경로 ·
runs 폴더 · 수요 파일 위치를 인자로 받고, 테스트가 임포트할 수 있어야 한다. 그래서 #29 의
`scripts/run_ue.py` 안에 있던 실행 로직을 `src/evdt/runner.py` 로 옮겼다.
`run_ue.py` · `sweep_ue.py` · `run_experiment.py` · `compare_stages.py` 는 이 모듈을 부르는
얇은 명령이다.

**`--soc` · `--demand-multiplier` 는 scenario_id 를 바꾸고, `--stage` 는 바꾸지 않는다** (#59).
앞의 둘은 **세계**를 바꾸므로 서로 덮어쓰면 안 되고, 스테이지는 같은 세계에서 **정책만**
바뀌므로 같은 이름을 공유해야 히트맵을 나란히 놓을 수 있다. 단계는 run_id 에 들어간다
(`<scenario>__UE__p100__s0007` / `<scenario>__S0__p100__s0007`).
두 단계를 한 표·한 그림으로 보려면 `scripts/compare_stages.py --seeds 1-20`.

## 5. 실제 결과 (경부 하행 · 설 2026 최대일 · −5 °C · 시드 1–20, 로컬 DB 393 km)

> ⚠ 아래 숫자는 **옛 노선(392.978 km)** 으로 만든 결과다. 중심선(415.058 km) 기준 결과와 차이는
> `docs/debug_centerlines_log.md` §5 (하행 평균 대기 65.6 → 118.3분).

| KPI | 출발 SoC 낮음 · 수요 ×1 (config 그대로) | 출발 SoC 높음 · 수요 ×3 |
|---|---|---|
| 평균 대기 (분) | 423.5 (417.3 – 429.6) | 65.6 (63.2 – 68.1) |
| P95 대기 (분) | 1,613 (1,586 – 1,640) | 249 (240 – 258) |
| 최악 휴게소 평균 대기 (분) | 940 (914 – 966) | 121 (116 – 127) |
| 병목 슬롯 (칸) | 178.1 (175.1 – 181.0) | 207.3 (202.3 – 212.4) |
| 몰림비 | 3.47 (3.40 – 3.54) | 1.46 (1.44 – 1.47) |
| 총 체류 (시간) | 54,770 (53,856 – 55,683) | 12,086 (11,698 – 12,474) |
| 충전 필요 EV (대) | 5,798 (5,772 – 5,825) | 6,726 (6,694 – 6,757) |
| UE 마지막 gap | 0.37% · 반복 1 | 1.61% · 반복 2 |

괄호 = 95% 신뢰구간. 40개 run 모두 수렴했다.

- **구간이 좁다.** 평균 대기의 구간 폭이 평균의 ±1.5% (낮음) · ±3.7% (높음). 시드 20개면
  두 조건의 차이를 말하기에 충분하다 — 두 구간은 어느 KPI 에서도 겹치지 않는다.
- **병목 슬롯은 높음·×3 이 더 많은데 대기는 훨씬 짧다.** 낮음은 몇 곳이 하루 종일 4시간 이상
  막히고, 높음·×3 은 많은 곳이 1~2시간씩 막힌다. "얼마나 넓게" 와 "얼마나 깊게" 가 다른 지표다.
- **⚠ 진입 EV 의 표준편차가 0 이다** (8,361 대, 25,086 대 고정). 생성기가 시간대별 대수를
  `교통량 × EV 비중` 의 반올림으로 고정하기 때문이다 (이슈 #20). 그래서 이 구간들은
  "도착 대수의 흔들림" 을 빼고 잰 것이라 실제보다 좁다. 생성기를 포아송으로 고치면 넓어진다.

히트맵 (`heatmap_wait.png`): 낮음은 서울~죽암(0~127 km)이 오후부터 끝까지 4시간+,
옥천 이남은 0. 높음·×3 은 망향~평사(72~291 km)가 넓게 막히고 서울 쪽과 경주 이남은 0.
큐 길이 히트맵 (`heatmap_queue.png`) 에서는 충전기가 많은 추풍령·김천·칠곡이 가장 짙다 —
대기는 비슷해도 줄 선 차 수는 충전기 수에 비례해서 길다. 두 그림을 같이 봐야 한다.
