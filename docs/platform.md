# 플랫폼 설계 — 시간축을 갈아끼우는 충전 쏠림 시험장

> 한 줄: **산출물은 "2026 설 분석 결과" 가 아니라, 기간 하나를 지정하면 그 기간의
> 실측을 끌어와 재현하고 엔진 사다리를 얹어 쏠림이 어떻게 풀리는지 보여주는 장치다.**

> ## 이 문서가 답하는 질문
>
> 멘토링에서 두 가지를 물으셨다.
>
> 1. **딜리버리를 어떻게 할 것인가** — 데이터 모델링과 대규모 최적화 작업의 산출물
> 2. **각자에게 이 프로젝트의 가치는 무엇인가** — 포트폴리오로 삼을 구간
>
> 1번의 답이 이 문서다. 2번은 §7 에 있다.

---

## 1. 우리는 이미 플랫폼을 만들고 있었다 — 선언한 적이 없을 뿐이다

`DESIGN §4.1` 의 **설계 규칙 다섯 개**는 전부 "갈아끼울 수 있게" 를 위한 것이다.
처음부터 그렇게 썼는데, 그걸 **산출물로 부른 적이 없다.**

| 설계 규칙 | 무엇을 갈아끼울 수 있게 하나 |
|---|---|
| 2. `world/` 는 `engine/` 을 임포트하지 않는다 | **엔진** — 시뮬레이터는 어느 단계가 도는지 모른다 |
| 4. 시뮬레이터와 뷰어 사이에 스냅샷 스트림 | **렌더러** — 2D·3D·GIF 를 바꿔도 시뮬레이터를 안 고친다 |
| 3. 모든 공간 엔티티에 `offset_km` + 위경도 | **시각화 차원** — 3D 를 나중에 붙여도 셀을 다시 안 나눈다 |
| 5. 재현 근거는 SQLite, Parquet 에는 재현 가능한 것만 | **실행 비교** — 어느 세계였는지 되짚을 수 있다 |
| 1. 큐 규칙은 단일 모듈 | 원장과 시뮬레이터가 **같은 미래**를 본다 |

여기에 둘이 더 있다.

- **가정 레이어** (#54) — 실측 위에 얹는 것은 **전부 이름이 붙고 모든 그림 부제에 찍힌다.**
  재현과 가정이 섞이지 않는다
- **`demand.period` 스위치** (#54) — 시간축이 **설정값 하나**다

> **이 둘이 "시간축을 갈아끼운다" 의 전부다.** 이미 있다.

## 2. 축 하나를 바꾸면 무엇이 따라오나

```
                    demand.period = chuseok2026
                              │
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
   fetch_traffic         build_tcs_od        fetch_chargers
   --label chuseok2026   (해당 기간)          (해당 시점 인벤토리)
          │                   │                   │
          ▼                   ▼                   ▼
   ┌──────────────────────────────────────────────────┐
   │  build_replay.py --period chuseok2026            │
   │    volume_*.csv · entry_exit_*.csv  (피크일 기준) │
   └──────────────────────────┬───────────────────────┘
                              ▼
                   재현 (UE) — 아무도 조정하지 않은 상태
                              │
          ┌───────────┬───────┴───────┬───────────┐
          ▼           ▼               ▼           ▼
         S0          S1              S2          S3
     (현재화면)   (예약원장)        (예측)    (한계외부비용)
          └───────────┴───────┬───────┴───────────┘
                              ▼
                  스냅샷 스트림 (설계 규칙 4)
                              │
                  ┌───────────┴───────────┐
                  ▼                       ▼
            2D 히트맵 · 지도          3D 디지털 트윈
```

### ⚠ 자동으로 안 따라오는 것 — 적어 두지 않으면 조용히 틀린다

`build_replay.py` 가 **스스로 경고한다**: *"기온 · 충전기 현황 · EV 비중은 따라오지
않는다."*

| | 왜 수동인가 |
|---|---|
| **기온** | 추석은 영상이다. 설의 −5°C 를 그대로 쓰면 **주행거리와 충전속도가 둘 다 틀린다** |
| **충전기 현황** | 시점이 다르면 기수가 다르다. 2026년 설치분 53기 문제(#64)가 여기 걸린다 |
| **EV 비중** | 반년이면 보급률이 움직인다 (#67) |

**이 셋을 자동화하는 것이 플랫폼의 남은 숙제다.** 지금은 사람이 config 를 고쳐야 하고,
고치는 걸 잊으면 **에러 없이 틀린 재현**이 나온다.

## 3. 계층 — 무엇이 무엇을 모르는가

```
  ┌──────────────────────────────────────────────┐
  │ 관측  스냅샷 스트림 → 2D · 3D · GIF           │  시뮬레이터를 모른다
  ├──────────────────────────────────────────────┤
  │ 엔진  UE · S0 · S1 · (S2 · S3 · S4)          │  세계를 못 바꾼다
  ├──────────────────────────────────────────────┤
  │ 세계  CTM 본선 + 휴게소 충전 큐 (Δt 루프)      │  어느 엔진이 도는지 모른다
  ├──────────────────────────────────────────────┤
  │ 수요  교통량 × EV 비중 × 목적지 × 진입 SoC     │  가정은 레이어로만 들어온다
  ├──────────────────────────────────────────────┤
  │ 실측  VDS · TCS OD · 충전기 인벤토리 · 충전 이용률 │
  └──────────────────────────────────────────────┘
```

**위로 갈수록 바꿔끼우기 쉽고, 아래로 갈수록 바꾸면 전부 다시 재야 한다.**
그게 #101 에서 배운 것이다 — `run_id` 는 세계를 구분하지 못하므로, 수요 계층을
건드리면 **그날 전부 다시 돌려야 한다.**

## 5. ⚠ 시간축을 바꾸는 것의 정직한 조건

#81 이 **시작 전에 못 박아 뒀다**:

> *"추석이 설보다 덜 막힐 수도 있다. 그때 조용히 설로 돌아가면 **결과를 보고 골랐다**
> 가 된다."*

**설이 조용해서 추석으로 간다** 면 그게 바로 그 함정이다. 그런데 **플랫폼으로 만들면
함정이 아니다** — 고르는 게 아니라 **축이 돌아간다는 것을 보이는 것**이고, **두 기간을
다 보고**하면 된다.

### 그리고 "설이 안 막혔다" 는 절반만 맞다

| | 2026 설 | 평시 (3월) |
|---|---:|---:|
| **본선 정체칸** (날짜별) | **2.96%** | 0.73% |
| 피크일 (2/15) | **7.02%** | — |
| **충전 대기** | ~0 | ~0 |

**교통은 평시의 4배로 막혔다. 안 막힌 것은 충전이다.**

> 그러므로 할 말은 *"데이터를 잘못 골랐다"* 가 아니라
> **"2026년 충전 수요는 아직 배정이 필요한 수준에 오지 않았고, 그 수준이 어디인지를
> 우리가 쟀다"** 다 — 충전 필요 7,252대 부근, 교통은 용량의 1.5배부터.

## 6. 키워드 다섯 개 — 어디에 서 있나

팀이 정한 발표 키워드를 **상태 라벨과 함께** 둔다. 숨기면 Q&A 가 찾아내고, 그러면
**진짜 있는 것까지 신뢰를 잃는다.**

| 키워드 | 상태 | 보여줄 것 |
|---|---|---|
| **거시 교통류 모델** | 구현·검증, **정체 재현 미달** | 속도 MAPE 14.4%, **용량 한계 곡선** (1.5배 정체 시작, 2.5배 포화) |
| **디지털 트윈** | ✅ 재현 + 시간축 스위치 | 이 문서의 §2 그림. **3D 가 붙으면 완성** |
| **롤링 호라이즌 최적화 엔진** | **2/4 칸** (UE·S0·S1) | S1 의 최악 절단 (577.7 → 169.0분), 계산 1.6분 |
| **경제 모델 기반 코스트 평가** | 부분 | 총 사회적 비용 역전 (S0 7,516h vs S1 7,291h). ⚠ 이탈비용 120분 근거 없음 |
| **단기 수요 예측** | ❌ **미착수** | — (S2) |

**정직한 문장:** *"사다리 4칸 중 2칸을 만들고 나머지는 설계를 고정했다. 각 칸이
**정보와 조율** 로 정의돼 있어 S0→S1 이 정확히 두 가지만 다르다."*

## 7. 포트폴리오 구간

멘토님의 2번 질문. **각자 깊게 가져갈 수 있는 덩어리**로 나눈다.

| 구간 | 무엇을 말할 수 있나 | 근거 |
|---|---|---|
| **OD 역추정** | 부족결정 역문제, 식별가능성, IPF, 누출 방지 검증 | #62 · #111 |
| **최적화 엔진** | 균형(UE) 구현, 예약 원장, **사회적 비용 설계** | #59 · #83 |
| **검증 하네스** | 재현성, 사전등록 기준, **자기 결과를 의심하는 장치** | #97 · #101 · #58 · #112 |
| **대규모 데이터 처리·시각화** | 스냅샷 계약, 2D·3D 렌더러 분리 | #48 · #103 · #87~#93 |

### 가장 어필이 센 것은 세 번째라고 본다

캡스톤에서 **자기 결과를 세 번 의심해서 세 번 다 잡은 팀**은 드물다.

| | 잡은 것 |
|---|---|
| #55 | 진입 SoC ← 충전 시작 SoC 혼동 (충전 필요 10,035 → 1,842) |
| #97 | 검증 스크립트가 **0행을 통과**시키고 있었다 |
| #100 | 통행거리를 맞췄더니 **도로 사용량 33% 가 사라졌다** |
| #101 | 같은 `run_id` 로 **다른 세계**가 돌고 있었다 |
| #111 | 기점 구성비 0.392 가 **맞춤 인공물**이었다 |

**그리고 전부 스스로 찾았고, 전부 숫자로 적었다.**
