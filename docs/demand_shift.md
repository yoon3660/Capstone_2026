# 기준선이 움직였다 — 실측 OD 수요로 다시 잰 값 (#101)

> 한 줄: **충전 필요 대수가 절반 아래로 떨어진다** — 하행 1,842 → 837 · 상행 2,310 → 984.
> 그리고 그 비율이 **모든 수요 구간에서 0.42~0.46 으로 일정하다.**

코드: `scripts/compare_demand.py` · `scripts/sweep_ue.py --od`

---

## 0. 먼저 — 첫 표가 틀렸다. 원인이 이 문서에서 가장 중요하다

처음 돌린 비교는 **충전 필요 10,112 → 860대(12분의 1)** 라고 했다. 실제는 **1,842 → 837** 이다.

### `run_id` 는 세계를 구분하지 않는다

```
run_id = (scenario_id, stage, 참여율, seed)      ← 이게 전부다
```

**yaml 을 고치면 이름은 그대로인데 세계가 바뀐다.**

| run_id | 돌린 날 | `departure_soc` | 충전 필요 |
|---|---|---|---:|
| `seollal_2026_down_base__UE__p100__s0001` | **2026-09-26** | `low` (0.3429) | **10,129** |
| 같은 이름 · 지금 config | — | `holiday` (0.6653) | **1,842** |

#55 가 기본값을 바꿨는데 **9월 run 이 "재현 기준선" 인 척 계속 제공되고 있었다.**
스크립트는 `DONE` 이라 건너뛰고 그 KPI 를 읽었다 — **OD 효과에 진입 SoC 수정이 통째로
섞인 표**였다.

### `check_same_world` 로는 안 걸린다

그 방어는 **진입 EV 수**를 본다. 이 경우 **18,534 로 같다.** 움직인 것은 충전이 필요한
부분집합뿐이다.

> `sweep_ue.py` 의 docstring 은 이미 같은 종류의 사고를 적어 두고 있었다 (#55 때
> #54 이전 run 이 두 칸에 남아 신뢰구간이 [1, 83] 로 터져서야 알아챘다).
> **그때 넣은 방어가 문제보다 좁았다.**

### 고친 방법

| | |
|---|---|
| `run_params(cfg)` | **run_id 가 구분 못 하는 것**을 기록한다 (SoC·수요배율·가정 레이어·od_profile) |
| `stale_reason(stored, cfg)` | 재사용 전에 대조하고 **다른 필드를 전부 이름으로** 말한다 |
| `reusable_run(db, run_id, cfg)` | 두 스크립트가 같이 쓴다 |

```
⚠ 기존 run 을 못 쓴다 (설정이 다르다 —
   departure_soc: 기록 'low' ≠ 지금 'holiday' ·
   departure_soc_mean: 기록 0.3429 ≠ 지금 0.6653)
```

**옛 run 에 없는 키는 불일치로 보지 않는다.** 나중에 추가된 필드가 없다고 전부 다시
돌리면 쓸 수 있는 결과까지 버린다.

> **검산:** 양쪽 arm 을 처음부터 다시 돌리니 옛 수요가 문서의 **1,842 · 2,310** 과
> 정확히 일치했다. 가드가 "다른 세계" 가 아니라 **맞는 세계**를 복원했다는 확인이다.

## 2. 수요 사다리 — 하행, EV 보급률 축 (시드 7)

| EV 비중 | 진입 EV | 옛 수요 충전필요 | **OD 수요** | 배율 | 옛 수렴 | OD 수렴 |
|---|---:|---:|---:|---:|---|---|
| 5% | 18,534 | 1,923 | **803** | 0.42 | ✅ | ✅ |
| 10% | 37,068 | 3,597 | **1,655** | 0.46 | ✅ | ✅ |
| 15% | 55,601 | 5,475 | **2,470** | 0.45 | ✅ | ✅ |
| 20% | 74,137 | 7,370 | **3,289** | 0.45 | ✅ | ✅ |
| 25% | 92,671 | 9,131 | **4,215** | 0.46 | ❌ gap 2.05% | ✅ |
| 30% | 111,205 | 10,844 | **4,754** | 0.44 | ❌ gap 7.07% | ✅ |

### 읽는 법 셋

**1. 비율이 일정하다.** 0.42~0.46 으로, 수요가 6배 늘어도 거의 안 변한다. 통행거리
분포를 고친 효과가 **수요 수준과 무관한 곱셈**으로 들어온다는 뜻이다.

**2. 하행은 양쪽 다 안 꺾인다.** EV 30% · 충전 필요 10,844대에서도 **병목 0칸**이다.
이건 `docs/s1.md` 에 적어 둔 것과 맞는다 — *"하행 균형 시나리오는 병목이 1.2칸이라
엔진이 일할 자리가 거의 없다"*.

> ⚠ `findings_sprint2.md` §7.5 의 **혼잡 하행 병목 120칸**과 헷갈리면 안 된다.
> 그쪽은 **기회 충전 레이어**가 같이 얹힌 시나리오이고 `gap_tol` 5% 의 **비균형**
> 실행이다. 이 사다리는 EV 보급률만 올린 것이고 전부 균형이다.

**3. 옛 수요가 ev25 부터 수렴하지 않는다. OD 수요는 전 구간 수렴한다.**
수요가 가벼워져서 선택이 덜 뒤집힌다 — 다만 *"OD 가 수렴을 고쳤다"* 로 읽으면 안 된다.
**같은 수요 수준에서 비교한 게 아니다** (옛 ev25 = 9,131대, OD ev25 = 4,215대).

## 3. 이것이 무엇을 움직이나

**지금까지의 모든 결론이 옛 수요 위에 서 있다.**

| | 어디에 적혀 있나 | 어떻게 되나 |
|---|---|---|
| *"2026 설엔 안 막혔다"* | `findings_sprint2.md` §1 | **더 강해진다** — 충전 수요가 절반이다 |
| 수요 사다리 · 꺾이는 지점 | `findings_sprint2.md` §7.5 | **다시 재야 한다** |
| S0 가 지는 이유 (#59) | `s0.md` | 구조는 그대로, **숫자는 다시** |
| S1 의 최악 절단 (#83) | `s1.md` | 〃 |

`findings_sprint2.md` 맨 위에 **"이 문서의 모든 숫자는 옛 수요 기준"** 을 박아 뒀다.

### #97 에서 예상한 방향 그대로다

> *"우리는 충전 수요를 약 1.6배 과대추정하고 있다. 결론이 보수적인 쪽으로 틀렸다."*

실제로는 **약 2.2배**였다 (1/0.45). 예상보다 크다. **그대로 보고한다** — #81 에서 세운
원칙과 같다. 쏠림이 보이는 쪽으로 고르지 않는다.

> 한산해지는 것이 나쁜 소식이 아니다. *"수요 축을 올려 가며 언제 꺾이는지를 잰다"* 는
> 지금 서사가 **더 중요해질 뿐**이다.

## 4. 다시 돌리는 법

```bash
# 재현 시나리오, 옛 수요 vs OD 수요, 시드 20
python scripts/compare_demand.py --config config/scenario_seollal_down.yaml --seeds 1-20
python scripts/compare_demand.py --config config/scenario_seollal_up.yaml   --seeds 1-20

# 수요 사다리 (--od 를 빼면 옛 수요)
python scripts/sweep_ue.py --config config/scenario_seollal_down.yaml \
    --soc holiday --dm 1 --ev-share 0.05 0.10 0.15 0.20 0.25 0.30 --od --seeds 7
```

### 고친 것 하나 더 — `--ev-share` 의 라벨이 틀려 있었다

`sweep_ue.py` 가 칸 라벨로 `cfg.demand.ev_share` 를 썼는데, #54 이후 EV 비중은 그 자리를
덮어쓰지 않고 **`ev_adoption` 레이어로 얹힌다.** 그래서 그 값은 **항상 실측 5%** 였고,
모든 칸이 `ev%=5` 로 묶여 `check_same_world` 가 *"같은 수요 배율인데 진입 EV 가 다르다"*
라는 **오탐**을 냈다. `effective_ev_share` 로 고쳤다.
